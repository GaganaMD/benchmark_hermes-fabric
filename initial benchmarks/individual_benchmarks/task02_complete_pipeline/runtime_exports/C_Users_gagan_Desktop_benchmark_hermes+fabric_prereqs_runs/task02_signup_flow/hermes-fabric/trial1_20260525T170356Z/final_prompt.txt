ANSWER:
When a new user signs up, the typical data flow across those layers is:

1. **`api/handlers.py` (request entrypoint)**
   - Receives the signup HTTP request (usually JSON body with fields like `email`, `password`, `name`).
   - Parses and validates request shape (or delegates to schema validation).
   - Calls a service-layer function in `services/user.py`, passing a clean DTO/model (not raw HTTP objects where possible).
   - Handles service exceptions and maps them to HTTP responses (e.g., `409` for duplicate email, `400` for invalid input, `201` on success).

2. **`services/user.py` (business logic)**
   - Implements signup rules:
     - checks whether user already exists (via `db/repo.py` query),
     - hashes password,
     - applies defaults (roles/status/profile fields),
     - may trigger side effects (verification token, welcome email, audit event).
   - Calls `db/repo.py` to persist the new user record.
   - Returns a domain object/result to the handler (often with sensitive fields removed, e.g., no password hash).

3. **`db/repo.py` (persistence layer)**
   - Contains DB-specific operations (SQL/ORM calls).
   - Reads: `get_user_by_email(email)` to detect duplicates.
   - Writes: `create_user(user_data)` inserting the row (email, password_hash, etc.).
   - Commits transaction and returns stored entity (often including generated `id`, timestamps).

4. **Return path back up**
   - `db/repo.py` returns persisted user → `services/user.py`.
   - `services/user.py` may transform to response-safe shape → `api/handlers.py`.
   - `api/handlers.py` returns HTTP response (e.g., `201 Created` with user id/profile, maybe auth token depending on design).

So conceptually: **HTTP input → handler validation/transport concerns → service business logic → repository DB I/O → service shaping → handler HTTP response**.
