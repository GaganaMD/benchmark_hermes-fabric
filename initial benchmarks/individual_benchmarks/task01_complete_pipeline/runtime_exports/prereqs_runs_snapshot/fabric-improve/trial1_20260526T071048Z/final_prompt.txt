## 1) High-level flow (5–8 bullets)

**Assumptions:** Python backend, `auth/jwt.py` handles token decode/verify + refresh issuance; access/refresh JWTs are distinct.

1. Client sends `Authorization: Bearer <access_token>` on protected API request.  
2. Auth middleware/dependency calls `validate_access_token(token)` in `auth/jwt.py`.  
3. Code parses JWT header, enforces allowed `alg`, selects key (possibly via `kid`), verifies signature.  
4. Code validates registered claims (`exp`, `nbf`, `iat`) with small leeway, then app claims (`iss`, `aud`, `sub`, `jti`, `type=access`).  
5. Code checks revocation/denylist state (e.g., by `jti` or session ID). If valid, request proceeds with identity/context attached.  
6. When access token expires, client calls refresh endpoint with `refresh_token`.  
7. Backend runs `validate_refresh_token`, enforces `type=refresh`, checks rotation/replay rules, then issues new access token (and usually new refresh token).  
8. Old refresh token is invalidated (single-use) and token family/session state is updated; anomalies trigger family-wide revocation.

### Typical interaction flow

```python
def validate_access_token(raw):
    claims = decode_and_verify(raw, expected_type="access")
    check_not_revoked(claims["jti"])
    return AuthContext(user_id=claims["sub"], scopes=claims.get("scp", []))
```

```python
def refresh_tokens(raw_refresh):
    claims = decode_and_verify(raw_refresh, expected_type="refresh")
    check_refresh_rotation_and_replay(claims)   # single-use + family rules
    mark_refresh_used(claims["jti"])
    new_access = issue_access_token(sub=claims["sub"], sid=claims.get("sid"))
    new_refresh = issue_refresh_token(sub=claims["sub"], family_id=claims["fid"], prev_jti=claims["jti"])
    return {"access_token": new_access, "refresh_token": new_refresh}
```

### What `decode_and_verify` usually does

1. Parse JWT header without trusting it.
2. Enforce algorithm allowlist (e.g., only `RS256`/`ES256`; avoid mixed HS/RS confusion).
3. Resolve verification key (`kid` lookup from JWKS or local keyring).
4. Verify signature.
5. Validate temporal claims (`exp`, `nbf`, `iat`) with leeway.
6. Validate issuer/audience and required claims.
7. Enforce token type claim (`typ`/`token_type`).

### Error handling pattern

- Normalize low-level library exceptions into domain exceptions:
  - `ExpiredSignatureError` -> `TokenExpired`
  - `InvalidAudienceError` / `InvalidIssuerError` -> `TokenInvalid`
  - Missing required claim -> `TokenInvalid`
  - Revoked jti -> `TokenRevoked`
- API layer maps these to 401/403 with generic message (avoid leak), while logs keep reason codes.

## 3) Validation details checklist

## Signature verification
- ✅ Verify cryptographic signature every time.
- ✅ Use trusted key source; validate `kid` exists and maps to active key.
- ❌ Never allow `alg=none`.

## Algorithm allowlist
- ✅ Hardcode acceptable algorithms (`ALLOWED_ALGS`).
- ✅ Ensure key type matches algorithm class (don’t verify RS token with HMAC secret).

## `exp`, `nbf`, `iat` + clock skew
- ✅ `exp` required for both access and refresh.
- ✅ `nbf`/`iat` sanity checked (not too far in future).
- ✅ Leeway (e.g., 30–120s) for clock skew.
- ✅ Optional max token age using `iat` (especially for refresh).

## `iss`, `aud`, `sub`, `jti`
- ✅ `iss` exact match.
- ✅ `aud` expected value(s), strict semantics.
- ✅ `sub` required and canonicalized (string user ID).
- ✅ `jti` required + unique, used for revocation/replay checks.

## Token type checks (`access` vs `refresh`)
- ✅ Explicit claim check (`token_type`/`typ`), not inferred from endpoint.
- ✅ Different TTL, claims, and verification path per type.

## Revocation / denylist
- ✅ Access token: optional denylist if short TTL; stronger if high-risk app.
- ✅ Refresh token: must be stateful (used/revoked/active family tracking).
- ✅ Fast lookup by `jti` and possibly `sid`/`fid`.

## 4) Refresh flow details

## Preconditions for refresh
- Refresh token is:
  - signature-valid
  - unexpired
  - `token_type=refresh`
  - issued by expected `iss` and `aud`
  - not revoked
  - not already used (if rotation enabled)

## Rotation strategy
- **Best practice:** single-use refresh tokens with **token family ID** (`fid`).
- On refresh:
  - old refresh `jti` marked used
  - new refresh issued with same `fid`, new `jti`, and `prev_jti` linkage

## Replay detection/invalidation
- If a previously used refresh token appears again:
  - flag replay
  - revoke entire token family/session (`fid`)
  - require re-authentication
- Store `used_at`, `replaced_by`, IP/device metadata for forensics.

## Access + refresh issuance + TTL
- Access TTL short (5–15 min typical).
- Refresh TTL longer (days/weeks), bounded by absolute session lifetime.
- Optional sliding session window with max absolute cap.

## 5) Failure modes and security pitfalls

- Accepting token without checking `aud`/`iss` → token confusion across services.
- Not enforcing algorithm allowlist → downgrade/none-alg attacks.
- Reusing refresh tokens (no rotation) → replay window.
- No `jti` or no persistence for refresh → cannot detect replay.
- Long-lived access tokens → poor revocation responsiveness.
- Returning verbose auth errors to clients → oracle/info leak.
- Not handling key rotation (`kid`) correctly → outages or bypass risk.
- Blind trust in `iat` with no future-bound check → weird clock abuse.
- Missing type checks (`refresh` accepted where `access` expected).
- Race conditions in refresh rotation (double-submit) without transactional updates.

## 7) Quick hardening recommendations (top 10)

1. Enforce strict `ALLOWED_ALGS` and disallow dynamic algorithm trust.
2. Require and validate `iss`, `aud`, `sub`, `jti`, `exp`, `token_type`.
3. Separate access and refresh verification paths and secrets/keys if feasible.
4. Implement single-use refresh rotation with token family tracking.
5. Add replay detection that revokes entire family on reuse.
6. Keep access TTL short; use refresh for continuity.
7. Add bounded leeway and future-`iat` checks.
8. Make refresh rotation updates transactional/atomic (prevent double-spend races).
9. Instrument structured logs + metrics for every auth decision.
10. Build a comprehensive negative-test suite (claim tampering, key mismatch, concurrent replay).
