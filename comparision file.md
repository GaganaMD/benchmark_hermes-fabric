## Summary for Presentation

| Setup                       | Expected Strength                                                                          | Expected Weakness                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| **Codex only**              | Fastest and often sufficient for small, well-scoped, test-backed tasks.                    | Less structured reporting; weaker explanation of verification and recovery. |
| **Fabric + Codex**          | Produces clearer prompts, stronger acceptance criteria, and more organized outputs.        | Can increase latency and sometimes over-specify simple tasks.               |
| **Hermes + Fabric + Codex** | Best audit trail: repo inspection, scoped execution, verification, and recovery summaries. | Usually slower because of orchestration and extra checks.                   |

## High-Level Expected Findings

1. **Codex only** is expected to be fastest overall.
2. **Fabric + Codex** is expected to improve output structure and acceptance-criteria adherence.
3. **Hermes + Fabric + Codex** is expected to produce the most supervisor-friendly execution summaries.
4. For simple tasks like T3–T6, raw Codex may be enough.
5. For ambiguous or multi-step tasks like T8–T10, Hermes + Fabric + Codex is likely to produce the strongest final result.
6. Fabric is most useful when the original prompt is vague, underspecified, or missing verification criteria.
7. Hermes is most useful when the benchmark needs auditability, recovery notes, and confirmation that scope boundaries were respected.
